# next: a daemon that serves a tree of JSON nodes, for any client

## Contract
One daemon per session owns every terminal. Clients (TUI, phone, CLI) connect over one stream and exchange JSON objects, one per line (`t`-tagged). The state is a tree of **nodes** opened on demand: `session` (level 0: workspaces with a summary) → `workspace` (level 1: its panes) → `pane` (level 2: its screen). Every node has `id` (uuid), `v` (its document version), `epoch` (changes at every daemon start), `rev` (counts changes), and `attention`.

**The envelope never changes** (`hello`, `open`/`close`, `snapshot`/`patch`/`gone`, `cmd`/`reply`, `error`). Evolution happens in node documents: additive fields never bump `v` and receivers ignore unknown fields; a breaking change adds `v+1` of that one node type, served beside the old. At `hello` the client lists the versions it reads per node type (`accepts`) and the daemon answers the version it will serve (`accepted`); a type without a common version is not served. There is no global protocol number.

A client opens a node and gets a `snapshot`, then `patch`es (RFC 6902 subset `add`/`remove`/`replace`, `from`→`to` rev) until it closes it. A patch never edits `rev`: the client applies the ops to the cached document it holds at `from`, then sets `rev` to `to`; any other state means reopen for a snapshot. Opening with `epoch`+`since` resumes from a cache: the daemon replies one `patch` (empty when nothing changed) when the epoch matches and the revision is still retained, else a `snapshot`. The epoch sent is the one in the cached document, never the connection's. Clients cache nodes by `(epoch, id)`.

**Attention** is a typed item the daemon computes once and a client never re-derives: `question`, `plan`, `permission`, `shell_done` (with `exit_code`), `agent_done`, `screen`, `merged`, `ci_failed`. Each names the node that opens when tapped and the `rev` that raised it. A node's `attention` lists its whole subtree, so it bubbles to the session. Looking is shared: a client that shows a node sends `mark_seen {node, rev}` and the daemon ends the attentions that node raised up to that revision, so every client clears them (the user's decision; the first proposal was a per-client *seen*). Each client also keeps a local record so it clears at once and while offline. An attention lasts as long as its cause (a `shell_done` ends when the next command starts), so the daemon drops it then; whether a person looked at it is the client's *seen*. There is no approve/deny anywhere.

**Shell blocks.** A shell pane can also be read as the commands it ran. When the shell reports its marks (below), the pane carries `blocks`, the id of a `blocks` node (type `blocks`, v1, opened on demand like any node): the pane's commands, newest last, each with its folder, start time, duration, exit status and output. The output is rows of styled spans (text with colour and bold, italic, underline), resolved by the daemon, so a client draws spans and needs no terminal emulator. A command that takes the whole screen (nvim) is a block with `full` and no output, and the node is in mode `full` while it runs: clients then draw the pane's screen node instead. The designs are `docs/prototypes/tui.html` (terminal and phone). The shell's input stays with the shell: a client's editor sends the line with `write` (text, then `\r`), stops a program with `write` of `^C`, and repeating or copying a block is the client's business. While the shell waits for a line, the pane node also says what it holds, `input: {text, cursor}`, so a client can draw the line in a field of its own (the terminal client does, N63; the phone's mirroring of it is OPEN-6) without the shell's prompt: the daemon notes where the shell says its prompt ends (OSC 133;B) and reads the line from there on the pane's screen.

**Changes.** The changes of a workspace's git repository are two more node types, opened on demand like any other. `open_diff {workspace, scope}` replies `{node}`, the id of a `diff` node (v1) that lists the files a scope changes: `uncommitted` (the working tree against `HEAD`, with the untracked files), `general` (this branch against its merge base with `origin/<default branch>`) or `commit` (with a `commit` id: what that commit changed). `open_commits {workspace}` replies the id of a `commits` node (v1): the branch's commits, newest first. Each file carries its path, its status (`added`, `modified`, `deleted`, `renamed` with `old_path`, `untracked`), counts of added and deleted lines, and its hunks, each line prefixed `+`, `-` or a space as in a unified diff. The daemon only reads git and shapes its output; a client numbers the lines from the hunk's starts, marks the words that changed and colours the syntax. A binary file, or one the daemon did not read, is a file with no hunks, and a diff over 2 MiB lists paths only. Looking is shared here too: `set_viewed` records a file's `hash` for that workspace and scope, and every client shows its `seen` (`yes`, or `changed` when the file differs from what was looked at). While a client has an `uncommitted` node open the daemon reads it every 2 seconds and patches what changed, so an agent's edits arrive by themselves; the other scopes are read when opened and on `refresh_diff`. The designs are `docs/prototypes/tui-diff.html` (terminal) and the Cambios screens of `docs/prototypes/mobile.html` (phone); the viewer of files and Markdown is a separate part (OPEN-9).

**Agent attention.** An agent the daemon starts (`claude`) is given hooks for that run only (`--settings` with a file the daemon writes; it merges with the person's own hooks and writes nothing to their settings). Each hook runs `jwn hook <event>`, which tells the daemon with `agent_event` what the agent is doing, for the pane named by the environment. The daemon, not the hook, turns that into attention: a permission prompt is `permission`, a question or a plan awaiting approval is `question` or `plan`, a finished turn is `agent_done`, and the agent moving on (a tool ran, a prompt was sent, the session or the program ended) ends what it had raised. A `claude` typed at a prompt has no hooks (RISK-29).

**Pull requests.** For each worktree workspace with a pane, the daemon looks every minute at the newest pull request of its branch with `gh` (the person's own login; the daemon holds no token) and raises `merged` when it was merged, or `ci_failed` when it is open and a check failed. It raises only when what it sees changes, so a mark a person has looked at does not come back; the old jw looked at merges only (`⚑`) and had no failed-CI mark.

**Closing, removing and looks.** A client can close a pane (`close_pane`), close a workspace (`remove_workspace`) and, for a worktree workspace, remove the worktree with it; the terminal client and the phone do all three (the phone since N54, asking first). A worktree is never removed by force: the client reads the `uncommitted` changes first and, when there are any, lists them and offers only to close the workspace; the branch stays, so commits not yet pushed are safe. The look of each client (a **mode**: system, dark or light; and a **theme** for each kind, chosen from the ten palettes of `contract/themes.json`: five dark ones (One Dark, Catppuccin Mocha, Tokyo Night, Gruvbox Dark, Solarized Dark) and five light ones (One Light, Catppuccin Latte, Tokyo Day, Gruvbox Light, Solarized Light), each saying which it is, so a selector lists only the kind in force) is a setting of that client, not of the daemon: the terminal's is the file `settings.json`, the phone's is kept on the phone, and neither changes the other. Several sessions in one daemon are not built (RAT-16). The designs are `docs/prototypes/tui-manage.html` (terminal) and, in `docs/prototypes/mobile.html`, the screens *Ajustes: tema y modo* and *Cerrar un panel*.

**The phone link from the terminal.** The terminal client turns the phone link on and pairs a phone itself (`m`), as `jwn pair` does: a box with the QR and the link, and the question of the six-digit code when a phone scans. The question comes to the person (the box opens by itself), and only `y`, pressed once the question has been on the screen for a moment, accepts. `jwn pair`, `jwn devices` and `jwn revoke` stay for use without the client. The design is `docs/prototypes/tui-phone.html`.

A **pane is a terminal**: its process is always the user's `$SHELL`; a program runs inside it (`running` and `last_program` carry it, and the pane's `title` is its name).

**A panel with a program.** `n` in the terminal client still makes a shell; `N` (after `^␣` from the terminal level) opens a menu, «panel nuevo», with the shell first and then the programs the person listed in `config.toml` (`claude` alone while there is no file): picking one asks the daemon for a pane that starts it, so the pane is still a shell that runs the program first and is a shell again when it ends. The list is the terminal client's own, as `settings.json` is (RAT-20); the daemon and the phone do not read it (the phone's `+` stays a shell, REQ-234). The design is the menu of `docs/prototypes/tui-levels.html`.

## Interfaces
Home of every shape is `contract/schema/contract.schema.json`; the examples are `contract/fixtures/{client,daemon,phone,bridge,invalid}`; the Rust types are `crates/contract/src/lib.rs`. Do not restate them here. The phone link adds `PhoneMsg` and `BridgeMsg` (`crates/contract/src/link.rs`). The QR link is `jwn://<ipv4>:<port>/<token>?fp=<64 hex>` for the private-address listener, `jwn://<tunnel host>/<token>` for the tunnel, and with both `jwn://<ipv4>:<port>/<token>?fp=<64 hex>&t=<tunnel host>`.

| Direction | `t` | Purpose |
|---|---|---|
| client→daemon | `hello` | `client`, `accepts: {type: [v]}` |
| | `open` / `close` | `node`, optional `epoch`+`since` to resume |
| | `cmd` | `id`, `cmd` (below) |
| daemon→client | `hello` | `epoch`, `root` (session id), `accepted: {type: v}` |
| | `snapshot` | a whole `node` |
| | `patch` | `node`, `epoch`, `from`, `to`, `ops` |
| | `gone` | node removed or unknown |
| | `reply` | `id`, `ok` + `result?` or `error{code,message}` |
| | `error` | a message with no `id` to reply to |

The `blocks` node: `pane`, `mode` (`blocks` or `full`), `blocks`: `Block {id, cmd, cwd, started, running, code?, ms?, truncated?, full?, interrupted?, restart?, out}`, `out` = rows of `Span {t, fg?, bg?, b?, i?, u?}`, colours a palette index (0 to 255) or `#rrggbb`. Everything is in `contract/schema/contract.schema.json`; examples in `contract/fixtures/daemon/{snapshot-blocks,snapshot-blocks-full,patch-blocks-append}.json`.

The pane's `input` (N63): `{text, cursor}`, optional and additive (a pane node of v1 gains it, nothing is bumped): `text` is what the shell holds after its prompt, the rows a wrap of the screen split joined and a hard line break as `\n`; `cursor` is the cursor's place in `text` in characters. It is absent while a command runs and for a shell that does not report its prompt (`crates/daemon/src/pty.rs`, `input_of`). A client of an older daemon sees no `input` and draws the screen's line instead.

Layout (N72): a `workspace` node gains `layout`, optional and additive: a tree whose leaves are exactly the node's `panes`, `{t: "pane", pane}` or `{t: "split", dir: "row"|"col", ratio, a, b}` (`row` puts `a` on the left and `b` on the right, `col` puts `a` above; `ratio` is the share of `a` in thousandths, 100 to 900). It is absent while the workspace has no panes and from a daemon that does not keep one, whose clients arrange the panes themselves. `new_pane` gains `beside` (a pane of the workspace) and `dir` (`row` when absent).

The `diff` node: `workspace`, `scope` (`uncommitted`, `general`, `commit`), `commit?`, `base?` (`origin/main`, for `general`), `state` (`ok`, or `no_base`), `too_large?`, `omitted?` (files left out of a too large diff), `files`: `DiffFile {path, old_path?, status, binary?, unreadable?, added, deleted, hash, seen?, hunks}`, `Hunk {context, old_start, old_lines, new_start, new_lines, lines}` with each line `+text`, `-text` or ` text`. The `commits` node: `workspace`, `base?`, `more?`, `commits`: `{sha, short, subject, time}` (time in Unix seconds). Examples in `contract/fixtures/daemon/{snapshot-diff*,snapshot-commits}.json`; the schema is home.

Commands (`cmd`): `rename_session`, `rename_workspace`, `rename_pane`, `swap_panes`, `grow_pane`, `sync_workspace`, `open_folder`, `list_dir`, `create_worktree`, `remove_workspace`, `new_pane`, `close_pane`, `write`, `resize`, `mark_seen`, `open_diff`, `open_commits`, `refresh_diff`, `set_viewed`, `agent_event`, and the phone link's `mobile_start`, `mobile_link`, `mobile_wait`, `mobile_answer`, `mobile_stop` (REQ-84). Error codes: `bad_request`, `not_found`, `unsupported`, `conflict`, `git_failed`, `io`.

Command semantics (N3): `open_folder` takes an absolute path of an existing directory and opens it once (`conflict` if open; `not_found`, `bad_request` for a missing path, a file or a relative path). `create_worktree` makes `<repo parent>/<repo name>-wt/<branch with / → ->` with `git worktree add` (a new branch from `base`, or an existing branch checked out, never both) and opens it as `<repo>: <branch>`; names that are options or not branch names are `bad_request`, git's own message is `git_failed`. `remove_workspace` closes a workspace; with `remove_worktree` it first runs `git worktree remove` without force, so a worktree with changes stays and so does its workspace. A successful open replies `result: {workspace, path}`.

Panes (N4): `new_pane` starts the user's `$SHELL` (else `/bin/sh`) in the workspace folder on a PTY (24×80 until `resize`, at most 500 each) with `TERM=xterm-256color` and `JWN_PANE_ID` set (`identity::env_var`), and replies `result: {pane}`. The pane node's `screen` is the vt100 screen as text rows. A shell that exits takes its pane with it, like closing a terminal; `close_pane` and `remove_workspace` end the shells. After a daemon restart the saved panes get a fresh shell with the same ids (the screen and scrollback are not kept). A shell that prints OSC 133 marks (`ESC ] 133 ; D ; <code> BEL` finished, `ESC ] 133 ; C BEL` command started) raises `shell_done` with the exit code, which the next command start ends; shell integration scripts that print them for zsh, bash and fish come later.

Changes (N32): `open_diff` and `open_commits` take a workspace whose folder is inside a git repository and reply `result: {node}`; the same workspace and scope give the same node while it exists. The daemon runs the user's own `git` (`crates/daemon/src/diff.rs`) with no pager, no colour, no external diff or textconv and `GIT_OPTIONAL_LOCKS=0`. `uncommitted` is `diff -M HEAD` (against the empty tree before the first commit) plus the files of `ls-files --others --exclude-standard`, read from disk (a symlink, or a file over 512 KiB, is `unreadable`; a file with a NUL in its first 8000 bytes is `binary`). `general` is `diff -M --merge-base origin/<base> HEAD`, with `<base>` taken from `origin/HEAD` (`no_base` when that is not set). `commit` is `show -M -m --first-parent --format=` of the id. The commits are `log -n 201` of `origin/<base>..HEAD`, or of `HEAD` with no base. Every read runs at the top of the repository the workspace is in, so a workspace that is a subfolder shows the repository's changes. A commit named by 4 to 40 hex digits is resolved to its full id, which is the node's `commit`, so one commit is one node however it was named. A file's `hash` is the first 16 hex digits of the SHA-256 of its path, status, rename source and lines. `set_viewed {node, path, viewed}` is `not_found` for a node, or a path in it, that is not there. A node nobody has opened 60 seconds after its creation, or after the last client closed it, is removed.

Agent hooks (N36): `agent_event {pane, event, notification_type?, tool?}` with `event` one of `notification`, `pre_tool_use`, `post_tool_use`, `user_prompt_submit`, `stop`, `session_end`. The settings file is `<state>/claude-hooks.json` (`crates/daemon/src/launch.rs`): `Notification` is asked for only `permission_prompt|elicitation_dialog|agent_needs_input` and `PreToolUse` only for `AskUserQuestion|ExitPlanMode`; the other hooks are asked for always, with a 5 s timeout. What each event raises (`crates/daemon/src/agents.rs`):

| Event | Ends first | Raises |
|---|---|---|
| `notification` `permission_prompt` | | `permission` (not while a `plan` or `question` is pending) |
| `notification` `elicitation_dialog`, `agent_needs_input` | | `question` |
| `pre_tool_use` `AskUserQuestion` | permission, question, plan, agent_done | `question` |
| `pre_tool_use` `ExitPlanMode` | the same | `plan` |
| `post_tool_use`, `user_prompt_submit`, `session_end` | the same | |
| `stop` | the same | `agent_done` |

Looks (N38): `settings.json` in `identity::config_dir()` is `{"mode": "system"|"dark"|"light", "dark": <id of a dark theme>, "light": <id of a light theme>}`, all optional: the mode picks the kind (`system` follows the machine) and the kind picks which of the two to draw with, so changing the mode brings back the theme last picked for it. The ten palettes are `contract/themes.json` (read by Rust through `contract::themes`; the phone's table follows in N41): per theme (`id`, `name`, `kind`: `dark` or `light`) the twelve colours `bg panel fg dim line sel blue green yellow red magenta cyan`, the ones `docs/prototypes/tui-manage.html` and `mobile.html` draw with. Closing and removing use the commands that exist: `close_pane {pane}`, `remove_workspace {workspace, remove_worktree?}` (N3), and `open_diff {workspace, scope: uncommitted}` to know whether a worktree is clean; no message changes.

Phone link in the terminal client (N42): `m` asks the daemon with `mobile_start` (reply `{uri, lan?, tunnel?, pending}`: at once over the network address while the tunnel opens in the daemon, N48), asks again with `mobile_link` until `pending` is false, listens with `mobile_wait` in slices of 2 seconds so that a stop is heard, answers with `mobile_answer` and stops with `mobile_stop`; all from a thread of its own over its own connection (`crates/jwn/src/tui/phone.rs`), because a link with no private address waits for the tunnel for up to 90 seconds. The QR is the link at the lowest level that fits, two rows of modules to a terminal line, drawn black on white with a two-module quiet zone whatever the theme.

Opening and making (N49): `create_worktree` takes an optional `folder`, the name of the worktree's folder inside `<repo>-wt/` (one path component, at most 80 characters, no control character; else `bad_request`); without it the folder is the branch with its slashes made dashes, as before. The terminal client's `w` sends the name it asked for as the folder and `feat/<name>` as the branch, from the branch of the workspace the person is in (`base`). Both `o` and `w` open the workspace they make with `new_pane`, and the client opens it as soon as the session shows it (`crates/jwn/src/tui/open.rs`).

Browsing the PC's folders (N50): `list_dir {path?, hidden?}` takes an absolute path (the daemon's `$HOME` when none) and replies `result: {path, parent?, home, dirs: [{name, git}], total}`: `path` is the canonical folder, `parent` is left out at `/`, `home` is the daemon's home (clients write it as `~`), `dirs` are its subfolders (links to folders included) sorted without regard to case, the first 500 of the `total`, `git` when the subfolder holds a `.git`. Names starting with a dot are left out unless `hidden`. A path that is relative or not a folder is `bad_request`, a missing one `not_found`, one the daemon cannot read `io`. A session's workspace summary carries `project` the same as its workspace node: the repository of a worktree, and the folder's own path when the folder is a repository's root (N52), so a client can tell which of its workspaces are repositories and make a worktree of one it has not opened (`crates/daemon/src/browse.rs`, `crates/daemon/src/core.rs`). The `session` node lists its workspaces grouped (`crates/daemon/src/grouping.rs`, REQ-219): clients draw the list as it comes.

Programs for a new panel (N60): `config.toml` in `identity::config_dir()` holds one `[[program]]` table per entry: `name` (the menu's label), `command` (a list of strings: the program and its arguments, sent as `new_pane`'s `program`) and optionally `key` (one lowercase letter). Unknown keys are ignored. The terminal client reads it (`crates/jwn/src/tui/programs.rs`) and never writes it; `new_pane` and the pane node do not change.

Entering (N46): `jwn` with no arguments, or `jwn tui`, is the terminal client. It connects to the daemon on the socket; when none answers it starts `jwn daemon` itself in the background (`crates/jwn/src/main.rs`), with no terminal to read from, its output in `<state>/daemon.log` and a process group of its own so that the hang-up of the terminal does not reach it, and waits up to 5 seconds for it.

Development link: with `JWN_TCP=127.0.0.1:7870` the daemon also listens on loopback TCP, and `adb reverse tcp:7870 tcp:7870` lets a phone on a cable reach it; any process on the machine can use it, so it is off by default and prints a warning. The phone gets pairing, TLS and the tunnel later.

The phone link (N22–N27): a **bridge** the daemon hosts (crate `web`) lets a phone reach the daemon away from a cable. The phone opens a WebSocket to the bridge (loopback, fronted by a Cloudflare quick tunnel that ends TLS; optionally also a TLS listener on the PC's private address with a self-signed certificate the phone pins), sends `pair` (first time) or `auth` (afterwards), and once the bridge answers `ready` every WebSocket text message is one daemon line, both ways. The bridge connects to the daemon's own socket only after the phone is authenticated. Pairing: `jwn pair` makes a one-use token and prints a QR link; the phone sends it with its name and a code it shows; the person at that terminal compares the code and answers `y`; only then a device secret is issued (the PC keeps its hash). `jwn devices` and `jwn revoke` manage them without a daemon.

Transport: JSON lines on a Unix socket (mode 0600, in a 0700 dir) whose path comes from `identity::socket_path()` (`crates/identity/src/lib.rs`). `session.json` in `identity::state_dir()` is private to the daemon (written whole, atomically; a file it cannot read is moved to `session.json.bad`, never overwritten). Client side: `crates/wire` (`Client` keeps the node cache and applies patches). The phone later carries the same objects one per WebSocket text message.

## Acceptance
- REQ-1  THE contract SHALL define every message and node as JSON Schema in `contract/schema/contract.schema.json`.
- REQ-2  THE contract crate SHALL parse every fixture in `fixtures/client` and `fixtures/daemon` and write back the identical JSON.
- REQ-3  THE contract crate SHALL validate every such fixture against the schema.
- REQ-4  IF a fixture in `fixtures/invalid` passes the schema, THEN the conformance suite SHALL fail.
- REQ-5  IF the schema has a message type, command, patch op, node type, attention kind or error code with no valid fixture, THEN the conformance suite SHALL fail.
- REQ-6  WHEN a document carries a field the receiver does not know, the receiver SHALL ignore it.
- REQ-7  THE envelope SHALL NOT change; a breaking change SHALL add a new `v` of one node type.
- REQ-8  WHEN a client sends `hello`, the daemon SHALL answer `accepted` with the highest version in common per node type and omit a type with none.
- REQ-9  WHEN a client opens a node with the daemon's `epoch` and a retained `since`, the daemon SHALL send one `patch`; otherwise a `snapshot`.
- REQ-10 WHEN a node's attention changes, the daemon SHALL patch it and every ancestor a client has open.
- REQ-11 THE daemon SHALL compute attention; a client SHALL NOT derive it.
- REQ-12 THE fixtures SHALL be plain files with no Rust dependency, so a Kotlin suite can read the same ones.
- REQ-13 THE product name, env prefix and paths SHALL come from `identity.toml` only.
- REQ-14 WHEN a pane starts, its process SHALL be the user's `$SHELL`.
- REQ-15 IF a daemon is already listening on the socket, THEN a second daemon SHALL refuse to start; a socket nobody listens on SHALL be cleared.
- REQ-16 WHEN the daemon restarts, the session id and workspaces SHALL be the same and the epoch new.
- REQ-17 IF a line is not a contract message, or comes before `hello`, THEN the daemon SHALL send `error` and keep the connection.
- REQ-19 WHEN `open_folder` names an existing directory not yet open, the daemon SHALL add a `folder` workspace and patch the session node.
- REQ-20 WHEN `create_worktree` succeeds, the daemon SHALL have a git worktree beside the repository and a `worktree` workspace for it.
- REQ-21 IF a worktree has changes, THEN `remove_workspace` with `remove_worktree` and without `force` SHALL fail with `git_failed` and change nothing (REQ-282).
- REQ-22 WHEN a workspace is removed, the daemon SHALL send `gone` for its node to whoever has it open.
- REQ-23 WHEN `new_pane` succeeds, the daemon SHALL have a live PTY running the shell in the workspace folder and a pane node whose `screen` follows its output.
- REQ-24 WHEN the shell of a pane exits, the daemon SHALL remove the pane.
- REQ-25 WHEN a pane's shell prints a command-finished mark, the daemon SHALL raise `shell_done` with its exit code on that pane and every ancestor; WHEN the next command starts, it SHALL end it.
- REQ-26 WHEN a pane or its workspace is removed, the daemon SHALL end its shell.
- REQ-27 WHEN the daemon restarts, each saved pane SHALL get a new shell under the same id.
- REQ-28 WHILE no node a client has open changes, the daemon SHALL send that client nothing.
- REQ-29 WHEN an item is added to or removed from the end of a list in a node, the patch SHALL be one `add` or `remove` op for it, not the whole list.
- REQ-30 THE daemon SHALL be drivable with JSON alone through the `jwn` binary: start, commands, stop, restart, state restored (`crates/jwn/tests/e2e.rs`).
- REQ-31 THE Kotlin contract module SHALL parse every valid fixture, write back the identical JSON, validate it against the same schema, reject the invalid ones, and apply every `patch-cases` file as Rust does (`android/contract`, `ConformanceTest`).
- REQ-32 IF a fixture or the schema changes without the Kotlin types following, THEN the Kotlin suite SHALL fail (Gradle treats `contract/` as a test input).
- REQ-33 WHILE a workspace has attention its phone has not seen, its Home row SHALL show the mark of the most urgent one, with a count when there are several, and one line saying what it is.
- REQ-34 WHEN the person taps the line that says an attention in a Home row or an item in Avisos, the phone SHALL open the node the attention names (the pane's tab, not only the workspace) and mark it seen on that phone.
- REQ-35 THE phone SHALL keep a local seen record, node id to revision; it SHALL treat an attention as seen when its `rev` is not above the recorded one, and SHALL drop the record of a node from another epoch.
- REQ-36 THE phone SHALL NOT offer approve or deny controls on Home or Avisos.
- REQ-37 THE pane screens (claude, dev, shell) SHALL stay as in `docs/prototypes/mobile.html`.
- REQ-38 (withdrawn) The pane key row (`^␣ esc tab ↑ ↓ ← → ^C`) is removed for now; where those keys go is OPEN-5. The editor's stop button (`■`, `^C`) stays.
- REQ-39 THE Android client SHALL draw Home, Avisos and a workspace's panes from the shared fixtures, under the application id and label of `identity.toml`, beside any other jw app.

- REQ-295 WHEN `grow_pane` arrives, THE daemon SHALL move the nearest split around the pane whose direction is `dir` so that the pane has `by` thousandths more of the split (less when negative), the share kept from 100 to 900; IF no split of that direction is around the pane, or `by` is out of range, THEN it SHALL answer `bad_request` and change nothing, and IF the pane is unknown, `not_found`.
- REQ-296 WHEN `H`, `J`, `K` or `L` is pressed at the panel level, THE terminal client SHALL send `swap_panes` with the focused panel and the one on that side (REQ-291), or say that there is no panel there and send nothing; WHEN `<`, `>`, `{` or `}` is pressed it SHALL send `grow_pane` for the focused panel, `row` for `<` `>` and `col` for `{` `}`, by -50 for `<` `{` and 50 for `>` `}`, and WHEN the daemon refuses it SHALL say there is no split that way for that panel.
- REQ-297 THE daemon SHALL keep the blocks of each shell pane on disk in `<state>/history/<pane id>.json`, written whole and atomically, in a folder only the person can enter and a file only the person can read (0700 and 0600), at once when a command starts or ends or the blocks are emptied, at most every 2 seconds for the output of one that runs, and all that changed when the daemon is stopped from inside; the file of a closed pane SHALL be removed, and so SHALL those of panes the session does not have when the daemon starts.
- REQ-298 WHEN the daemon starts and a restored pane has a saved history, THE pane's `blocks` node SHALL have those blocks from the start, without waiting for a prompt and in the order they had, ahead of what the new shell runs, the ids going on after the last one.
- REQ-299 WHERE a block was running when it was saved, THE daemon SHALL bring it back as `interrupted`, not running, with no `code` and with `ms` what it had run until the save.
- REQ-300 WHEN a history is restored, THE daemon SHALL add after it a block with `restart` (no command, `started` the time of the start), unless the last block already is one, and SHALL add nothing when no block was saved; the limits of REQ-57 and of 4 MiB SHALL hold for what is restored.
- REQ-301 THE terminal client and the phone SHALL draw a block with `restart` as one line across the list that says «el daemon se reinició» and how long ago, which cannot be selected, and a block with `interrupted` as «interrumpido», with the time it had run when that is a second or more, apart from the colours of a command that ended (the terminal client's bar grey, the phone's label yellow).
- REQ-302 IF a history file cannot be read, THEN THE daemon SHALL move it aside to `<pane id>.json.bad`, say so on its standard error and start the pane with no history.
- REQ-303 WHEN `clear` empties a pane's blocks (REQ-273), THE saved history SHALL be empty too.
- REQ-304 WHEN the left button is pressed on a command or an output line of a pane's list of blocks in the terminal client, it SHALL begin a drag in that pane and let go of what was selected before; a press anywhere else SHALL be the click it always was and let go of it too.
- REQ-305 WHILE a drag is held, THE terminal client SHALL select from where it began to the line and column under the pointer, over the command and output lines only, the first line from the column it began on, the last up to and including the column it is on and the lines between whole; WHEN the pointer is above or below the list it SHALL select to its first or last line shown and scroll it a line every 60 milliseconds while it stays there; the selection SHALL stay in the pane it began in.
- REQ-306 WHEN the button is let go after the pointer moved, THE terminal client SHALL copy what is selected through OSC 52, the command lines without their prompt mark, the folder and time lines, the notes and the gaps left out and the lines joined by line breaks, and say «copiado · N líneas · M caracteres»; IF nothing that can be selected was covered, THEN it SHALL copy nothing; WHEN the pointer never moved, the press SHALL be the click it was.
- REQ-307 THE selection SHALL stay lit until the next press or key (`esc` included) and the wheel SHALL not let go of it.
- REQ-308 THE terminal client SHALL light a selection with the colour, among the six accents of the theme in force, that shows best against the theme's ground, and write on it in the ground colour or the text colour, whichever has the greater contrast with it; on each of the ten themes both SHALL have a contrast of at least 3 to 1.
- REQ-83 THE phone SHALL keep its device secret in Keystore-backed storage and SHALL pair from the QR link's text (from the QR the camera reads or from pasted text).
- REQ-84 THE bridge SHALL answer a `mobile_*` command from a phone with an `unsupported` error and not pass it on; THE daemon SHALL end the tunnel it started when it is stopped, and the next start SHALL end one a dead daemon left (recorded in `<state>/tunnel.pid`).
- REQ-85 WHEN a phone pairs, it SHALL show the six-digit code it sent and wait for the PC; WHEN the bridge denies it or the PC cannot be reached, it SHALL say which of expired, declined, locked out, no longer paired or unreachable happened; WHEN the PC revokes it, the phone SHALL forget the pairing and say so.
- REQ-18 IF a client's outbox is full, THEN the daemon SHALL disconnect that client and no other.

## Rationale
- RAT-1 **Fixtures, not generated code, are the contract.** Generated Kotlin from a schema is poor and hides drift; two hand-written sets of types checked against the same files cannot drift without a red test. The round trip (parse then write equals the file) catches a field one side drops.
- RAT-2 **A frozen envelope with versioned documents** (the user's point) means no forced daemon stop when a client or a document changes. The old jw bumped `PROTOCOL` 25 times, each refusing the old peer. A new daemon binary still needs a restart to run (it owns the PTYs), but nothing forces it for a JSON change.
- RAT-3 **JSON lines**, not length-prefixed frames with a binary kind: readable with `nc -U`, no framing code. Raw terminal bytes are not needed while a pane's screen is a node of text rows; add a stream only when a UI proves it needs one.
- RAT-4 **Looking is shared** (the user's call, replacing the first proposal of a per-client seen): if the phone cleared an aviso and the terminal kept showing it, the person would clear it twice. `mark_seen` carries the revision looked at, so an attention raised after the look stays. The cost is that a person who looks on one device no longer sees it as new on another.
- RAT-5 **RFC 6902 subset** is known, small, and easy to apply in Kotlin; array edits go by index and are safe because a patch always applies on exactly `from`.
- RAT-6 **One daemon is one session** in v1: a second session is a second daemon and socket (`JWN_SOCKET`). The session node's id is stable across restarts; its `epoch` is not.
- RAT-7 **The shell is the pane's process, and a program is started by it, not typed at it**: `$SHELL -i -c '<program>; exec $SHELL -i'` has no keystrokes to race the prompt or echo, still reads the rc files (`-i`), keeps the pane alive when the program ends (`exec` turns the same process into a shell), and does not depend on the shell's prompt. Each word is single-quoted for the shell that reads it (fish escapes inside the quotes, the POSIX shells close and reopen them). The id passed to a new agent is explicit, so two agents in one folder never share a transcript, and a restart resumes with `--resume`, never a reused `--session-id`.
- RAT-8 **Spans, not bytes.** The old jw kept each block's raw bytes and every phone ran its own terminal emulator (a Kotlin module with golden tests to keep it equal to the daemon's). Resolving colours once in the daemon (it already runs vt100) means clients draw runs of text and the terminal client, the phone and a future web client cannot disagree. The cost is a larger document per block, bounded by REQ-57.
- RAT-9 **Standard marks.** OSC 133 is what other terminals' shell integrations speak; the command text and folder use OSC 633 (VS Code's `E` and `P`) because 133 carries neither. The old jw used a private OSC 7770 and only for zsh; one set of marks now covers three shells.
- RAT-10 **A separate node, a field on the pane.** Blocks can be large and change on every line of output; keeping them out of the pane node keeps the pane's screen patches small and lets a client that only draws the screen never open them. The pane says where they are (`blocks`) so a client does not guess.
- RAT-11 **The editor is the client's, the line is the shell's.** The shell keeps its history, completion and key bindings; a client sends the finished line. Mirroring the shell's own buffer both ways (what the old jw did with zle's `$BUFFER`) is left for later (OPEN-6).
- RAT-12 **Two node types and four commands, not one reply.** A diff as the reply of a command would be read once and be stale; as a node it is opened like any other, patched when it changes (an agent's edits arrive on their own) and cached by clients with the same resume rules. The cost is that the node has to be made first: the command names the workspace and scope, and the daemon keeps one node per pair while someone uses it. The old jw answered a `diff` request and the phone asked again.
- RAT-13 **Lines as prefixed strings, no numbers.** `"+text"` is a third of the size of `{"k":"add","text":…,"old":…,"new":…}`, and the numbers follow from the hunk's starts, so a client that derives them cannot disagree with the daemon. Words changed and syntax colours are drawn by each client: they are a way of drawing, not data.
- RAT-14 **Marks belong to a file's content, not to a person.** `hash` covers the path, status and lines, so a file that changes after it was looked at says so (`changed`) without anyone comparing, and the mark is shared like attention (RAT-4): looking on the terminal clears it on the phone. The old jw kept them per phone.
- RAT-15 **Hooks for this run, and the daemon decides.** `--settings` is the one way to give an agent hooks without editing the person's own settings, and it merges with theirs; the file is read, not written, by claude. The hook command only forwards the event's name and two fields, so what an event means (and any later change to it) lives in one place, the daemon, and is tested with JSON alone. A prompt for permission and a plan are both permission requests, so the more specific one wins (REQ-134). The old jw passed hooks the same way but kept only `working`, `waiting` and `idle`, so it could not tell a question from a permission or say a plan was ready.
- RAT-16 (the sidebar says nothing of sessions since N47: its `^␣ s sessions` was a leftover with no key behind it) **One daemon is still one session** (RAT-6); the user decided on 2026-10-14, after asking whether several were needed. Worktrees already group by project and the finder (`^␣ ␣`) changes workspace fast; hiding the workspaces of another session would hide their attentions, which is what the product is for; and a session in the contract means more nodes and UI in two clients and a migration. What the old jw's sessions gave (a named list one daemon served, filtered by the client) is a client view, cheap to add later if a person keeps over about 30 workspaces or needs contexts that share one attention list (OPEN-10). Anyone who wants two separate contexts today runs a second daemon with its own `JWN_SOCKET`.
- RAT-17 **Looks are per client, closing is not.** A theme is taste of the screen it is shown on (the phone in daylight, the terminal in a dark room), so each client keeps its own and `settings.json` is read by the terminal client, not the daemon; the ten palettes are one file both read so they cannot drift (RAT-1). Each palette says whether it is dark or light (the user's call, 2026-10-14): a selector that offered a light theme in dark mode would be offering what the mode forbids, and with the kind written in the file neither client has to guess it from the colours. Closing a workspace or removing a worktree is left to the terminal (the user's call): a thumb on a phone is the wrong place for something that deletes a folder, and the phone only closes a pane. A worktree is never removed by force (the user's call): the old jw's `--force` threw uncommitted work away, so here a dirty worktree stays and the client offers to close the workspace only.

- RAT-18 **Pairing is a question for the person at the PC, so it comes to them and cannot be answered by accident.** `jwn pair` was a command in another terminal, which the person had to know to run; as part of the client it is `m`. The box opens by itself when a phone asks, since a question nobody sees is a pairing nobody can accept; but a key typed for something else (the `y` of closing a pane, a letter typed into a shell) must not accept it, so a question waits for the one already open, and `y` counts only after 0.8 seconds. Any other key refuses: the safe answer is the easy one.
- RAT-19 **The phone browses the PC's folders through the daemon, and only folders.** The terminal client reads the disk it runs beside; a phone is on another machine, so `list_dir` is one more command, and every other client that is not on the daemon's machine can use it. It lists folders only because the phone's job there is to open a workspace; reading a file is the viewer (OPEN-9). The terminal's browser and `list_dir` share one reading (`daemon::browse`), so they cannot disagree about what a folder holds. The phone first could not tell whether a folder was a repository, so it offered a worktree of any workspace and showed what git said (RISK-33); since N52 the daemon says it in `project` (REQ-222).
- RAT-20 **The programs are a file the person edits, read by the terminal client.** The user asked for it on 2026-10-15: a pane is always a shell, and `N` offers preconfigured programs (claude and the commands that start it) instead of a key per program. It is a file of its own, not part of `settings.json`: the client rewrites that whole file whenever a theme is chosen (REQ-152), which would erase what the person wrote by hand, and TOML takes comments and a `command` as a list, so there is no shell quoting to get wrong (the daemon quotes each word itself, REQ-50). Entries replace the built-in list instead of adding to it, so a person who does not use claude is not offered it. A file that does not read keeps the list the client had: a typo mid-edit (the client reads every 2 seconds) must not empty a menu that was working, and the reason is shown where the person will look. The phone is left out on purpose (its `+` is a shell, decided in N56); a list shared by both would be a daemon-side file and a new message, for later.
- RAT-21 **The line says what is asked of you, in colour, and the row is the button.** The user (2026-10-15) found the bordered «ir ›» pointless on a workspace's row and wanted the interaction seen in a colour that says it needs reviewing; a tinted strip and a row of its own were tried in the prototype and both rejected for «only the text», inside the same row under the detail. The colour follows what is asked and not the mark's tone: a permission's `!` is red and a plan's `◆` magenta, but both are a decision, and a decision is the one thing that must not look like the rest (yellow), a failure is red, and everything that only waits to be looked at is cyan (the colour of the merged flag; the prototype offers magenta and green and the user did not pick another). A tap target of its own is kept for the line (it opens the pane, not just the workspace) and it still gives the row's menu on a long press, so a person does not lose the menu by pressing on it.
- RAT-22 **The field draws the shell's line; it does not own it.** The user (2026-10-15) wanted the terminal's field like the phone's today, and chose that the shell stays the owner of the line (history, completion and its key bindings keep working: RAT-11) over a client-owned text like the phone's. To draw only what is typed, without the user's own prompt, the client needs to know where it starts, and the pane's screen alone cannot say: the prompt is the shell's. The daemon reads it where it already has the exact moment, the reader of the PTY, which processes the bytes in order and sees the prompt-end mark with the screen exactly at it; and it finds the first row of the line from the wraps of the screen, not from a row noted at that time, because a line that wraps at the bottom scrolls the screen and a noted row would be wrong in the commonest case. The text travels in the pane node, which already changes with every key, instead of a node of its own. The phone could draw it too (OPEN-6) and is not changed here.
- RAT-23 **The loading is decided by the client from what the daemon already sends.** A program that draws on the normal screen (claude) leaves the shell's screen in the pane until it paints, and since N62 the node is `full` from the moment the command is reported, so that old screen is exactly what the person saw for the first second (the user, 2026-10-15: «se ve la terminal original»; reproduced on a private daemon: 74 ms to 1.5 s). The user chose a loading over a blank screen. The running block's `out` is already the program's own output, resolved by the daemon, so «has painted» is «a row has more than blanks», with no new field and no new message; the client remembers per command that it painted (the program may clear its screen) and gives up after 20 s (a program that is quiet, like `ssh` waiting for a host, must not hide its screen for ever). The alternate-screen programs (nvim, htop) start on a blank screen of their own and have no loading. The phone's stop (REQ-262) is what its text promises.
- RAT-24 **A program that leaves its screen and takes a moment to end is «closing», for any program.** N64 hid the shell's old screen while a program starts; the same screen came back at the other end (the user, 2026-10-15, and «cualquier programa», with `nvim` and `mole` as examples): the real claude leaves the alternate screen at once and takes about 1.2 s to end (measured frame by frame in the terminal client: 158 ms after the second `^C` the pane showed the shell's prompt and `❯ claude`, until 1384 ms), and the node stays `full` until the shell says the command ended (REQ-251). The daemon already knows when a program enters and leaves the alternate screen; it says it in the one place a client reads each frame, the pane's `screen` (`alt`, additive, no version bump), and the client does the rest. The signal is the alternate screen and not a list of names, so it works for every program that uses it (claude, nvim, htop, lazygit, the screens of mole). The client counts the 3 s itself, from when it saw the program leave, so a program that leaves on purpose and keeps running (a shell inside nvim) is not hidden for good. The phone is not changed in this part (the user: the problem is in the terminal client); its `Screen` type carries `alt` and the same rule can be applied there.
- RAT-25 **The daemon is the terminal, so it answers the terminal's questions.** Measured, not assumed (2026-10-15, the user: «con nvim no muestra el de cerrar»): neovim, before it leaves, writes `CSI c` (primary device attributes) as a sync point and waits for the answer up to a second; the pane's terminal never answered, so every `:q` took 1.05 s with the screen frozen, and the same query ends the start of most TUI libraries (the real claude painted at 1.75 s without answers and at 1.15 s with them in a plain pty). Answering costs nothing, and it removes the wait instead of drawing it (N64, N65): `nvim` quits in 0.10 s (1.11 s before) and `claude` ends in 1.00 s (1.52 s) in a real daemon. What is answered has a fixed or a cheap answer. The colours (OSC 10, 11, 4) are not: they are the theme of the client that happens to be looking (a pane has none, or several), and a program that is told a background decides its palette from it, so a wrong answer changes what it draws; a program that asks colours together with the device attributes sees the attributes come back alone and concludes there is no colour query, which is what it concluded before. The cursor's place is read where the query stood in the output, not at the end of the read, because that is what the program asked about. The answers go through a channel to a thread that writes them under the writer's lock (REQ-268): the reader holding the lock of the input while a client's `write` is blocked on a full terminal input would stop draining the output of a program that is itself blocked writing it.
- RAT-26 **Drawing and reading cost what is shown and what changed, not what is held.** The user had to close `jwn` with the laptop slow (2026-10-15). A profile (`sample`) of a terminal client with a pane of 100 large blocks showed it at 100 % of a core and 412 MB while idle, in deserialising JSON and allocating, not in drawing: every turn of its loop (every 40 ms) cloned and parsed every document again, the blocks of the pane included, whether or not anything had changed (REQ-269); and each frame then built the lines of all the blocks to show thirty (REQ-272). The daemon, with a noisy command, spent its time in turning the running block's whole screen (up to 500 rows) into spans once per read (`block_of`), and it read each pane's screen and blocks once per event of a batch when the batch is there to be read once (REQ-270). The array diff compared lists position by position, so the oldest block dropping off a full list made every block differ from the one before it and the patch (and the 256 kept of them) hold the whole list (REQ-271). Measured on a release build, 160 commands of 600 lines each in one pane, idle: terminal client 100 % CPU and 412 MB before, 2 % and 67 MB after; a command that prints 1.5 million lines with a client attached took 116.7 s and the daemon 116.6 s of CPU before, 4.7 s and 3.8 s after. The limits (100 blocks, 4 MiB, 256 revisions) are the same: memory was bounded, not leaking.
- RAT-27 **«Sync» is a push, nothing else.** The user (2026-10-15) has no use for bringing a base's changes into a worktree: what the worktree has done is what has to be somewhere else. So `s` is `git push`, never forced, and what the remote has that the worktree has not stays for the person to bring with git in a pane, where a conflict can be seen. The push runs in a connection and a thread of its own because a network push may take as long as it likes and the terminal client has one thread: on the shared connection the spinner would stop and the screen would not answer. A push that has nothing ahead is not sent: it is answered from what git already knows, with no network.
- RAT-28 **The branch is what stays, the folder is what can be lost.** Removing a worktree takes its folder and never its branch (REQ-147), so commits that were not pushed are not at risk: the box says they stay. What is lost is what was not committed, and that is the one thing git refuses to take without `--force`. The user (2026-10-15) asked to be able to remove such a worktree after typing its name, as a repository is deleted on GitHub: the name is a speed bump against a key pressed by habit, and the daemon does nothing about it (the client sends `force` only after it). The phone sends no `force`: a worktree with changes is still refused there.
- RAT-29 **The layout is the daemon's, and is brought to agree instead of kept up to date.** The user (2026-10-15) wants the panels split, swapped and resized, and wants a project to open with a layout (`.jw.toml`, part 13): so it has to outlive the terminal client and be the same for every client, which is what the daemon keeps. Panes come and go in many places (a new one, a closed one, one whose shell would not start after a restart, a session saved before layouts), so one `reconcile` after every change gives each of them the right outcome (a closed pane's room goes to its neighbour) instead of every place having to remember it. A ratio is in thousandths so it is an integer in a JSON patch and equal on every machine. Directions are by where the boxes are on the screen, not by number: with splits the number says nothing about where a panel is. The phone has tabs and ignores the tree.
- RAT-30 **What the daemon saves is what a client would see.** The user (2026-10-15) wants a pane's history to survive the daemon, and the blocks are the history. They are saved as the blocks node has them (spans resolved, a running block as it is), a file for each pane so that `session.json` does not grow and a pane's history goes with the pane. A command that was running cannot be known to have ended, so it is kept as cut and says how long it ran as far as the daemon knew; a program that had the whole screen has no output to keep (`full`), and the shell's own screen starts afresh. The mark of a restart is a block, not a new node or a flag of the list, so a phone that does not know it shows an empty block instead of breaking, and ids stay unique. The time is told as «hace 2 h» and not as a clock time because no client here knows the person's time zone.
- RAT-31 **A press that may be a drag waits to be a click.** The terminal client used to act on the press (focus a panel, pick a block); with a drag possible it cannot know yet, so a press on text only records where it began and the click, if the pointer never moves, happens when the button is let go, at the cell it began on. A press on anything that is not selectable is the click at once, so nothing else changed. The selection is kept as lines counted from the first of the list and columns of the text, not as pixels or rows of the screen, so a scroll while it is held does not move it. The colour is chosen by contrast and not named (a fixed yellow would be invisible on a light theme, a fixed blue on a dark one) and the text on it is the ground or the text colour, whichever reads: «most visible for the theme» is the user's (2026-10-15). The copy is OSC 52, as the blocks' `c` and `o` already are, which Ghostty honours.

### Mobile UI (the simple version)
A pane is a zsh (the user's `$SHELL`); claude or nvim run inside it, so the tab shows what runs there and the screen is a terminal. The claude-style conversation view comes when the daemon detects an agent in a pane, not from a role. Design baseline and the thing to approve: `docs/prototypes/mobile.html` (REQ-33 to REQ-38). The mark glyphs are `!` permission, `?` question, `◆` plan, `❯` command done (`✗` on a non-zero exit), `✓` agent done, `…` screen, `⚑` merged, `✗` CI failed; the existing `✻` agent and `⚡` dev stay. Only `shell_done` has a producer in the daemon today.

## Risks
- RISK-1 Index-based patch paths break if a client applies a patch to a node at a revision other than `from`. Mitigation: a client that sees a gap drops the node and reopens it for a snapshot.
- RISK-2 Round-trip equality forbids unknown fields inside valid fixtures, so forward-compatibility is tested by one synthetic test (`unknown_fields_are_ignored`), not by fixtures.
- RISK-3 `Attention.rev` assumes `rev` is monotonic per node across restarts; a restart changes `epoch`, so caches and *seen* maps are keyed by `(epoch, id)` and discarded on change.
- RISK-5 Patches are diffed from whole rebuilt documents on every change: simple and always consistent with the snapshot, but O(documents) per change. Fine at 25 workspaces; N5 measures it.
- RISK-6 `jwn stop` ends the daemon with SIGTERM and does not remove the socket or pid file; the next start clears a stale socket, and `stop` only signals a pid while the socket answers.
- RISK-7 `restore` drops a pane whose shell cannot start (say its folder is gone) and saves that, so a transient failure loses the pane; its workspace stays.
- RISK-8 A pane's `cwd` is where its shell started, not where it is now (needs shell integration); `title` is the shell's name until OSC titles are read.
- RISK-9 The loopback TCP listener has no authentication: any local process controls every pane. Development only; the real phone link needs pairing and TLS first.
- RISK-10 The Android live source is a development link (fixed address, no pairing); it has no UI tests, and it was checked by hand on a phone against the terminal client.
- RISK-11 (the mode of a blocks node no longer waits for this look since N62, REQ-250, REQ-251; `running`, the title and `last_program` still do) The program is the foreground process group of the terminal, looked at every 0.7 s with one `ps`; its argv is `ps` output split on spaces (quotes are lost), and a program shorter than the interval can be missed. Unix only.
- RISK-12 Only an agent with a known conversation comes back: one started through `new_pane` (we give it an id) or typed with `--resume <id>`/`--session-id <id>`. A plain `claude` typed at a prompt is shown as running but not resumed. Whether a conversation exists is a look for `<id>.jsonl` under Claude's `projects/` directory, which is Claude's layout, not a contract.
- RISK-17 A pane has one size, and the last client to ask sets it: the terminal client fits the pane to its box when it takes the keyboard, so the phone then draws a screen of that size. Per-client sizes need blocks (the phone draws spans, not the screen) or a screen per client.
- RISK-16 The fish integration (`shell/fish/jwn.fish`) was written on a machine without fish. Its first run (N35, fish 4.0.2 on Linux) passes the shared shell test, with two things found: the test had used bash syntax, and fish 4 marks prompts and command starts itself, with the start before our script can name the command, so the scanner lets a second start mark name the command an empty first one began. A fish older than 4 (no native marks) has not been run; the test skips a shell that is not installed.
- RISK-13 (measured: three blocks, one of 300 lines, are a 9 KB snapshot, and a short command is patches of about 330 and 270 bytes; the cost for a 100-block pane is not measured yet.) The daemon rebuilds and diffs whole documents on each change (RISK-5); a `blocks` node with 100 blocks of 500 rows is large. A command printing continuously changes one block every 20 ms. Measure with the real node (N17) and, if it hurts, diff only the changed block.
- RISK-14 The integration adds hooks to the user's shell (zsh `ZDOTDIR` shim, bash `--rcfile` wrapper, fish `--init-command`) and the user's own rc files must still run. Prompt frameworks (starship, powerlevel10k) also use these hooks; the order may matter.
- RISK-15 A program that redraws in place (progress bars with cursor moves) is rendered by the daemon's vt100, so its rows are the final screen, not every intermediate frame.
- RISK-18 A quick tunnel has no SLA and a new host name each run; a phone that stored the old one reaches the PC only over the private address until it is paired again or `endpoints` arrives. Registered can come about 60 s before DNS resolves (REQ-80 waits for it).
- RISK-19 A lost phone keeps full access until `jwn revoke`: the secret does not expire, and the phone can control every pane (it could read any file the daemon's user can through a shell).
- RISK-20 Anyone on the same network can reach the private-address listener (the pairing token and the person's `y` are what stop them), and the self-signed certificate is trusted only through the QR's `fp`.
- RISK-21 A daemon killed without stopping (SIGKILL, or SIGTERM sent by hand rather than through `jwn stop`) leaves `cloudflared` running until the next `jwn pair` ends it by the pid in `tunnel.pid`; the pid is signalled only while it still looks like a tunnel.
- RISK-22 With a device paired, the daemon listens on the private address whenever it runs (REQ-89), not only while `jwn pair` is open: what stops a stranger on the network is the device secret, the rate limit and the pairing token, as in RISK-20. `jwn pair stop` ends it until the next start. A tunnel host changes at every start, so a phone that is away learns the new one only from `endpoints` while it can still reach the PC.
- RISK-23 A `diff` node is rebuilt whole and diffed on each read (RISK-5), and a file inserted at the start of `files` shifts every index, so one new file can patch as large as the node (up to 2 MiB). Reads happen only while a client watches `uncommitted`, every 2 seconds, and a patch is sent only when the content changed; measured on this repository (N32): General of 203 files is a 1.1 MB snapshot read in 0.2 s, Sin commitear read in 0.09 s; a patch over the tunnel is not measured yet.
- RISK-24 `git diff HEAD` on a huge working tree takes noticeable time every 2 seconds while the node is open; the read runs without the hub lock, so other clients are not held, but the poll can lag behind the interval.
- RISK-25 Untracked files are read from disk by the daemon, not by git: a file being written while it is read can show a partial last line; the next read corrects it.
- RISK-26 The viewer's requests to the daemon (`open_diff` reads git) run in the terminal client's loop and wait up to 20 seconds, so a very large repository freezes the screen, and the live updates of the panes with it, while a view is first read. The node comes back in the next frame; a worker thread would remove the pause.
- RISK-27 `ChangesModel` and the screen decode a `diff` document each time they read it (the node cache keeps documents as JSON), up to three times per redraw for the tabs' counts; a 1 MB diff costs tens of milliseconds per redraw on the phone. A decoded copy kept per revision would remove it.
- RISK-30 `mergedAt` is not read (older `gh` prints a zero time for a pull request never merged); `state` decides. A pull request is looked at with one `gh` call a minute per worktree in use, a use of the person's GitHub quota; many worktrees open make many calls. What was last seen is not saved, so a restarted daemon raises `merged` or `ci_failed` again once for what it finds. A cancelled or skipped run is not a failure, and a check that is still running is not one yet, so a pull request whose only red check was cancelled shows nothing. The shape of `gh`'s JSON was checked against a real open and a real merged pull request of this repository; the commit-status shape (`state`) is from `gh`'s documentation.
- RISK-29 Only an agent the daemon started has hooks: a `claude` typed at a prompt has none and raises no attention (it also has no conversation id for a restart, RISK-12). Of the events, `UserPromptSubmit`, `PreToolUse`, `PostToolUse` and `Stop` were seen firing with a real claude (2.1.299) through the daemon, and `agent_done` reached the pane; the `Notification` types and the tool names `AskUserQuestion` and `ExitPlanMode` are taken from Claude's documentation and were not triggered live. `PostToolUse` runs `jwn hook` after every tool, one process each.
- RISK-28 (closed by N39 and N41) The terminal client closes panes (`x`) and so does the phone (the `×` of its tab).
- RISK-31 A worktree seen clean may get changes before `remove_workspace` arrives; the daemon does not force, so git refuses and the client shows its message (REQ-146), which is the only guard. The sixteen named colours a command prints (palette indices 0 to 15 in a block's spans) are the theme's; black and bright white turn into the text colour on a light theme. The diff's tints are the ground with a little green or red in it (`look.rs`), not table entries, so a theme cannot get them wrong. The terminal client asks the machine for its appearance with one command (`defaults read -g AppleInterfaceStyle` on macOS); on Linux it cannot tell and stays dark, and a terminal that is light while the machine is dark is the person's to fix with the mode.
- RISK-32 The QR of the real link is large: with the tunnel and the private address the link is about 170 characters, a code of 57 modules, 33 terminal lines and 61 columns with its quiet zone, and the box needs more beside it. A terminal smaller than that shows the link without the QR (REQ-160), and the prototype's QR is only a drawing. Each `m` that finds the link off makes a new one-use token; the box of a link already on shows the token it had.
- RISK-33 (resolved by N52) The phone offered a worktree of any folder and showed git's refusal for one that is not a repository. `project` now tells which workspaces are repositories (REQ-222, REQ-225); a repository's `.git` is looked for on each rebuild of the documents (one stat per folder workspace), and a folder that gains or loses its `.git` while open changes group when the documents are next built.
- RISK-34 The keyboard's rules (REQ-236, REQ-237) have no test and a text field added without `keepsKeyboard()` loses its own focus on the tap that focuses it (the root takes the focus away at the end of every tap that nothing claimed). A tap in the middle of a drag-and-drop or a long press also counts as a tap that nothing claimed when it ends without moving.
- RISK-35 An entry's `name` labels the menu only: the pane's title is the foreground program the daemon finds by polling `ps` (RISK-11), so `command = ["sh", "-c", "…"]` shows as its first word and a program that ends at once leaves a plain shell. Carrying the name to the pane would add a field to `new_pane`. A `command` that does not exist is not caught: the shell says so and the pane stays a shell (RAT-7).
- RISK-36 The line of attention is a text of about 20 dp high inside a row 50 dp high, so its tap target is smaller than the 48 dp the platform recommends; a tap just beside it opens the workspace instead of the pane. Avisos, where the whole row opens the pane, is the way to be sure.
- RISK-37 The mode follows the command's first word as the shell reports it, so `cd x && claude`, `FOO=1 nvim` or `time less` are found only by the 0.7 s look (RISK-11) and show as a block for up to that long; and a command that the shell does not report (an integration that failed, REQ-55) never gets the mode from the command at all. The pane's `screen` and the node's `mode` still travel in separate messages, so a client may draw one frame of the pane's older screen on a switch; not seen, only inferred from the order of messages.
- RISK-38 `input` is read from the screen, so a right prompt (`RPROMPT`) drawn on the first row of the line shows in it as text after a gap, a buffer with hard line breaks is read from its last row only (its first row's prompt column does not apply), and a screen that was resized after the prompt ended keeps the old column. The text of a shell that never reports its prompt end is the screen's line, with the prompt in it (REQ-258). The field counts characters and not columns, so wide characters (CJK) wrap late. While a command runs what is typed goes to the command and the field cannot show it.
- RISK-39 Once claude has painted, its screen is the pane's whole screen, and claude draws below what was already there, so the shell's history shows above its interface; the loading only hides the screen while nothing is drawn. Starting with a blank screen would hide it, and is left for a later part if the history is in the way. A program whose first output is only blanks or escape sequences is `starting` until its first text. The phone gives up after 20 s on its own timer (its clock is not the PC's), the terminal by the block's start time.
- RISK-40 A program that leaves the alternate screen for a moment and stays (nvim `:!cmd`, a pager asked to run something) shows «cerrando <program>…» for up to 3 s, and a program that is quick to end (nvim) shows it for a frame or not at all; one that never uses the alternate screen (a program on the normal screen) is never «closing» and its old screen cannot be told apart from its own. The phone still shows the shell's screen in that second.
- RISK-41 A program that is not at a terminal that can take input (a shell at its prompt) receives an answer as typed text, as with a real terminal: `printf '\e[c'` at a prompt puts `^[[?62;22c` on the line, and `cat` of a file that holds queries answers them. The reply to `CSI > q` names the terminal as the product (`jwn(0.0.1)`) and a program that chooses features by that name does not know it. A mode is answered «not recognised» for every number, including those the screen tracks (bracketed paste, the mouse): a program that asks first and then does without loses those.
- RISK-42 The daemon still builds, serialises and compares every node of the tree at each refresh (at most once per 20 ms batch), so a pane of large blocks costs its size at each one, and about 180 MB of the daemon's memory is that pane's blocks held three times (the store, the view and the document). A guess at the front drop that is wrong gives a larger patch and never a wrong one; a list that loses more than 8 items at its front at once is patched item by item as before. The terminal client still holds each document twice (the client's JSON and the parsed node).
- RISK-43 A push may wait for something the daemon cannot give: a password, a passphrase, an unknown host. `GIT_TERMINAL_PROMPT=0` and the daemon having no terminal make git fail instead, but an SSH agent or a credential helper that asks through a window can wait; the client gives up after 120 seconds and says so, and the push may still finish. It is not guarded further.
- RISK-44 The tree has proportions, not sizes, so two terminal clients of different sizes draw the same arrangement at different cell counts, and which panel is on the left of another is the same for both but «the longer side» (`n`) is each client's own. A pane that shrinks under a few cells still draws a box with no room in it; the minimum is one cell of the split, not of what a shell needs.
- RISK-45 The blocks on disk hold whatever the commands printed, secrets included, for as long as the pane lives: the file is for the person alone (REQ-297) but is not encrypted, and a backup of the state folder takes it. Up to 4 MiB of JSON are serialised under the daemon's lock for each pane that changed, every 2 seconds at most, so a very noisy pane costs that much each time (not measured: `/perf-review` before trusting it with many noisy panes); `jwn stop` ends the daemon with a signal and the daemon does not save once more, so the output of a running command is kept up to the last 2 seconds (the command itself, and every command that started or ended, is kept at once); a block running at the crash is kept as it was at the last save.
- RISK-46 The selection is counted in lines from the first of the list: when the oldest blocks are dropped from the front (the 100-block limit) while it is lit, the same line numbers are other text, and it moves. A terminal that does not report the pointer moving with the button down (it needs the button-event mouse mode) gives no drag, only the click. The terminal's own selection (shift-drag in Ghostty) never reaches this client.
- RISK-4 The Kotlin conformance suite proves the types and the patch rules, not a live connection; the live flows of the phone are checked by hand against a real daemon (RISK-10).
